2. 首期范围与默认选择

  • 只在用户点击时发请求，不做启动自动检查、后台任务、轮询、通知或红点。
  • 正式版支持检测及外部下载；Debug 显示当前版本及“调试版本不支持应用内检查更新”，按钮禁用，避免引导安装签名不兼容的正式包。
  • 发现更新后需用户点击“前往下载”。不内置下载器、安装器，不申请安装包权限，不自动卸载或安装。
  • 接入 Ktor Client；后续 Debug、Release 构建均只支持 ARM64、X86_64，停止打包和支持 32 位原生依赖。

  • 服务端没有更新日志、强制更新、最低系统版本、校验和或签名字段；首期只展示接口真实提供的信息。

4. 请求与响应约定

GET https://zp.ntutn.top/api/v1/updates
    ?software=so-novel-reader
    &os=Android
    &arch=ARM64
    &packageType=apk
Accept: application/json

以上 arch 是示例，实际采用第 5 节解析结果。固定 HTTPS 源，不提供用户编辑服务器地址入口；无需登录、Cookie、PoW 或管理员令牌。查询不发送当前版本、设备标识、书籍信息或阅读进度。

字段客户端要求
itemsHTTP 200 时必须是非空数组；多项时直接选择 items[0]，只解析和校验第一项，忽略后续项的业务结构。空数组、缺失或非数组为无效响应。
items[0].software / os / arch / packageType与本次四个查询值严格一致，不跨架构、跨类型选包。
latest.packageType必须为 apk。
latest.versionCode必须是十进制数字字符串，可无损解析为正 Long；拒绝负数、小数、溢出及数值 JSON 类型。
latest.versionName非空白字符串，仅用于展示。
latest.distributionTitle字符串，用作分发标题；允许空字符串，空时不展示。
latest.downloadUrl绝对 HTTP/HTTPS URL，必须有 host 且无 userInfo；拒绝 intent、file、content、javascript 及相对地址。HTTP 下载符合服务端约定，可交由外部浏览器处理；发布方优先提供 HTTPS。
latest.packageSize可缺失或为 null；非负 Long 十进制字符串时展示；格式错误视为无效响应，不能影响版本比较精度。
新增字段允许未知字段；不依赖分发 ID、包 ID、发布时间排序。

使用 Ktor Client（OkHttp 引擎）执行挂起请求，配置 HttpTimeout：连接与 socket 超时各 10 秒，请求超时 25 秒；整个响应读取另受 25 秒协程超时约束，超时或取消时取消请求并释放响应资源。响应体最多 64 KiB，通过流式读取限量后再交给 kotlinx.serialization，不信任 Content-Length，不先无界 bodyAsText()。禁止接口自动重定向和缓存，非 200 均不得进入成功判断；Ktor 不安装自动重试插件，同时关闭 OkHttp 引擎的连接失败自动重试。

多项响应保持服务端原始顺序，不排序、不求最大值、不扫描匹配项。第一项维度或字段无效时，整次检查报响应异常，不回退第二项；后续项即使版本更高也不参与比较。完整响应仍必须是合法 JSON 且满足 64 KiB 上限。HTTP 409 仍按错误处理，不属于成功响应的多项选择。

5. 版本、架构和发布规则

5.1 数值比较

通过 PackageManager 读取安装包的 versionName 和 longVersionCode。只有远端 versionCode > 本机 longVersionCode 才认为有更新；相等为最新版，低于本机不提供降级。不能比较 versionName、字符串字典序或发布时间。

5.2 仅支持 64 位的构建与架构解析

从本次功能版本起，在 app 的 defaultConfig.ndk 中配置 ABI 白名单，对 Debug、Release、APK 和 AAB 一致生效：

ndk {
    abiFilters += listOf("arm64-v8a", "x86_64")
}

排除依赖 AAR 中的 armeabi-v7a、x86 及其他非白名单 JNI 库；保留依赖的 Java/Kotlin 代码和两种 64 位库。不删除必要的整个依赖、不手工修改 Gradle 缓存，也不只在更新请求层过滤。构建产物必须实际不含 32 位库；32 位系统与仅提供 32 位应用 ABI 的设备此后不再支持安装和更新。

按安装包实际原生库目录识别 ABI，并用进程位数交叉检查。不能直接把设备支持的首个 64 位 ABI 当作当前安装 ABI，也不能在查询失败后尝试另一架构或省略 arch。

本机安装识别查询行为
64 位进程，nativeLibraryDir 尾段为 arm64ARM64允许检查。
64 位进程，nativeLibraryDir 尾段为 x86_64X86_64允许检查。
异常的 32 位运行环境，或未知目录不请求“当前安装架构暂不支持检查更新”。不误映射 ARM64。

目录识别需在 64 位真机与模拟器确认；若无可识别目录则明确不支持，不增加猜测性 fallback。32 位旧版不再获得新包；无需扩展服务端 ARM32/X86 枚举，不要求卸载旧版或迁移数据来规避架构限制。支持 64 位的设备上，旧版到新版的覆盖升级与数据保留纳入验收。

5.3 发布方约束

  • 拟定软件内部名 so-novel-reader，展示名沿用应用名称。内部名是新约定，不能根据 applicationId 自动推断服务端已经存在。
  • 发布包指定 os=Android、packageType=apk，声明真实包含的 ARM64 / X86_64 目标；同一个通用 APK 可同时登记两种架构。
  • 上传正式签名 APK，不将 AAB、Debug APK 或未分类历史包作为 apk 更新目标；使用本项目已有 ntutn.top 签名身份，保持 applicationId 和签名证书一致。
  • 版本码取 APK 实际值并递增。当前为 1，验证真正升级需发布更高版本的实际 APK；不能只把服务端 versionCode 伪填为 2。
  • 同一架构 / 类型序列不得存在最高版本冲突。签名兼容和最低系统版本由发布方保证，当前接口无法让客户端提前验证。

6. 异常语义与文案

结果用户提示含义
404 SOFTWARE_NOT_FOUND更新服务尚未配置此应用。当前线上已实际观察到；不是“已是最新版”。
404 NO_MATCHING_PACKAGE暂无适用于当前安装的更新包。软件存在，但本序列暂无包。
409 AMBIGUOUS_LATEST更新包配置冲突，请稍后重试。不挑选任意候选。
400 / 其他 4xx更新检查失败，请稍后重试。保留状态码便于本地诊断，不直接展示服务端原始错误。
429 / 5xx更新服务暂时不可用，请稍后重试。不自动重试；429 若有有效 Retry-After，在该时间内禁用重试，忽略无效值。
断网、DNS、TLS、超时无法连接更新服务，请检查网络后重试。保留当前安装版本。
3xx、HTML、非法 JSON、字段不符、超限响应更新服务返回异常，请稍后重试。不当作成功或无更新，不打开链接。
协程取消 / 页面所属 ViewModel 销毁不提示错误。释放请求资源，不把取消吞掉后写入错误状态。

重新检查时清除旧结果的下载入口，检查失败后不得继续展示旧结果为本次成功结果。已有浏览器下载不受后续检查影响。

7. 实现建议与文件职责

Ktor 依赖通过版本目录统一管理：运行时使用 ktor-client-core、ktor-client-okhttp；测试使用 ktor-client-mock，均采用同一 Ktor 版本。实现时选择与项目 Kotlin/协程兼容的稳定版本并验证构建。JSON 在限量读取后解析为 JsonElement，仅对选中的第一项转换业务模型，避免后续项的业务结构影响结果。

HttpClient 在 AppContainer 中创建并复用，checker 只借用，不按点击重复创建或关闭全局客户端；测试注入 MockEngine 并由测试负责关闭。关闭客户端/引擎两层重定向与自动重试，不安装 HttpCache；错误响应允许读取有界 JSON 后统一映射状态。

8. 验收与验证计划

  1. 协议单测：远端版本高于、等于、低于本机；9 与 10 的数值比较；Long 边界及溢出；非法 versionCode、空白版本名、非法 URL、错误查询维度、空数组；多项时只取第一项，首项无效不回退，后续项结构异常或版本更高均不影响首项结果；未知扩展字段、packageSize 缺失和 null。
  2. 架构及产物：ARM64、X86_64 正确映射，异常 32 位环境及未知目录不请求。检查 Debug/Release APK 的 lib/ 和 AAB 的 base/lib/，仅含 arm64-v8a、x86_64，预期原生库在两种 ABI 下齐全，不能存在 armeabi-v7a 或 x86。至少在 ARM64 真机和 X86_64 模拟器验证启动及基本阅读；支持 64 位的设备验证从旧版覆盖升级后数据保留。
  3. 网络测试：Ktor MockEngine 验证请求参数、状态码与响应解析；本地假服务配合真实 OkHttp 引擎验证超时、取消、重定向、无自动重试及流式大小上限。覆盖 200、404 两种错误码、409、429、503、重定向、HTML、断开、超时和超过 64 KiB；不依赖线上写入伪数据。
  4. 状态及 UI：连续点击只发一次；Checking 可见；取消不报错；旋转不重复请求/弹窗；离开设置不弹窗；错误可重试；失败清除旧下载入口。
  5. 下载：只在确认后打开返回的链接；取消保持应用；无浏览器给出提示；Debug 禁用正式更新流程。
  6. 本机构建：运行相关 JVM 测试、Debug 编译、--no-configuration-cache :app:verifyReleaseSigning :app:assembleRelease，校验正式 APK 签名和版本；运行 python3 scripts/check_file_lines.py。
  7. 线上只读联调：当前验证 SOFTWARE_NOT_FOUND 的真实路径；发布方备妥实际新 APK 后再验成功响应、下载链接和架构匹配。未完成前，验收记录必须写明成功升级链路尚未验证。
  8. 端到端升级：在有旧版与阅读数据的设备上，从新入口下载并由用户确认安装，验证签名兼容、版本增长、书库/进度保留；仅在有实际新版本包且获准设备安装时执行。

9. 已确认的决策

  • 已按用户评审明确：网络接入 Ktor Client；过滤 32 位原生依赖并停止支持；成功响应有多项时选择第一项。

  • 软件内部名拟定为 so-novel-reader；若需要其他名字，应在实现与服务端注册前统一。
  • 后续所有构建仅支持 ARM64、X86_64，过滤 32 位原生依赖；正式版提供更新，Debug 禁用更新，不借用另一架构或独立 Debug 软件名。
